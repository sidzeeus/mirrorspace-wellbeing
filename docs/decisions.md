# Decisions

The locked decisions for this project, each with a short rationale and the date it was recorded. `README.md` Part A is the source. Change a decision here first, then mirror it in `CLAUDE.md`.

When something is ambiguous during the build, the safer and more private option is chosen and added to "Build-time decisions" below.

## Locked decisions

| # | Topic | Decision | Rationale | Date |
|---|---|---|---|---|
| D1 | Age policy | 18+ only for the prototype. Age confirmation at registration. No minors' data collected. | Children's data under India's DPDP Rules may need verifiable guardian consent; excluding minors avoids that until a lawyer has reviewed it. | 2026-10-12 |
| D2 | Authentication | Django session cookies + CSRF. Same site or sibling subdomains, `SameSite=Lax`, `Secure`, `HttpOnly`. No JWT in `localStorage`. Strict CORS allowlist. | An `HttpOnly` cookie cannot be read by injected script, so a cross-site scripting bug cannot steal the session the way it could steal a stored token. | 2026-10-12 |
| D3 | Weekly contact email content | Only display name, week covered, "checked in X of 7 days", and one fixed neutral line. Student previews and confirms before the first send; can pause or revoke at any time. | The email shows that the student is using the app and nothing about how they feel, so it cannot expose mood, notes or any inferred risk. | 2026-10-12 |
| D4 | Check-in free-text notes | Omitted in the MVP. Structured fields only (mood, sleep, energy, stress). | Free text is the most sensitive and hardest data to protect; not collecting it removes the risk entirely. | 2026-10-12 |
| D5 | Deletion vs audit retention | On deletion, all user content is deleted or queued for deletion. Audit and consent events are pseudonymized (one-way hash, no message bodies), kept 12 months, then purged. | Honors the right to deletion while keeping enough evidence to show that consent was handled properly. | 2026-10-12 |
| D6 | Trusted-contact flow | Double opt-in. Unsubscribe link in every email. Rate limits on adding contacts and on SOS sends. | A contact must agree before receiving anything, which prevents the app being used to send unwanted email to a third party. | 2026-10-12 |
| D7 | Offline safety | Safety plan and verified helplines available offline through a PWA service worker. Required. | The moment someone needs support is often the moment the connection is poor. | 2026-10-12 |
| D8 | Automated risk detection | Out of scope. No automatic alerts. Crisis-like chat content triggers a fixed, non-AI response with the user's own safety plan and verified resources. | A classifier will be wrong in both directions, and alerting people without a staffed human response process is unsafe and a breach of trust. | 2026-10-12 |
| D9 | MVP cut line | Phases 1 to 3 and their frontend first. Chat (Phase 4) and Indian-language content afterwards. i18n foundation from the start. | The core loop and its safety boundaries must work before an AI feature is layered on top. | 2026-10-12 |
| D10 | Free text to providers | Never sent to analytics or error tracking. Chat content goes to the AI provider only, with minimal context. Transcripts off by default. | Each third party that receives student text is another place it can leak or be retained. | 2026-10-12 |
| D11 | Languages | English first. `next-intl` so other languages are added by translation files only. Fluent-speaker review before release. | Wellbeing wording that is mistranslated can mislead or harm, so machine translation is never shipped as final. | 2026-10-12 |

## Build-time decisions

Choices made while building where the specification was silent or contradictory.

| # | Topic | Decision | Rationale | Date |
|---|---|---|---|---|
| B1 | Check-in "optional note" in blueprint section 3 and section 6 | Not built. D4 applies. | Part A overrides Part E for decisions. | 2026-10-12 |
| B2 | Blueprint API lists `DELETE /api/v1/sharing/consent/{id}` | Revoking sets `status=revoked` and `revoked_at`; the row is kept. | Consent history must stay visible to the student (non-negotiable 2, README C.6). | 2026-10-12 |
| B3 | Product name | The repository folder name `mirrorspace` is treated as a working name only. User-facing copy uses a single configurable app-name string. | No name was specified; a single string keeps renaming cheap. | 2026-10-12 |
| B4 | Registering with an email that already has an account | The API gives the same 201 reply either way. No second account is made; the real owner gets an email saying someone tried. Resend-verification and password-reset replies are equally uniform. | Having an account in a wellbeing app is itself sensitive, so nobody should be able to test whether a given person uses it. | 2026-10-12 |
| B5 | Accounts that never confirm their email | Deleted automatically after 7 days (`UNVERIFIED_ACCOUNT_TTL_DAYS`). | Data minimization: an address typed by mistake, or by someone else, is not kept. | 2026-10-12 |
| B6 | Tokens in emailed links | Carried in the URL fragment (`#token=...`), not the query string. | Browsers never send the fragment to a server, so tokens stay out of access logs and Referer headers. | 2026-10-12 |
| B7 | Session lifetime | Idle timeout of 7 days, renewed on each request (`SESSION_COOKIE_AGE_SECONDS`). | Short enough to limit exposure on a shared or lost phone, long enough not to lock out a weekly user. | 2026-10-12 |
| B8 | Account deletion | Requires the current password. The account is locked and every session ended immediately; a background task erases the data, and an hourly sweep completes any erase whose task was lost. | Deletion is irreversible, so it needs proof of identity; and it must take effect even if the queue is down. | 2026-10-12 |
| B9 | Sign-in before email confirmation | Not allowed. Completing a password reset also confirms the email. | Stops someone registering with another person's address and using the account. | 2026-10-12 |
| B10 | OpenAPI schema in production | Staff only. Public in local and test. | The route list is useful to the team and of no use to students. | 2026-10-12 |
| B11 | Django admin | Shows that an account exists and can lock it. Profiles and wellbeing data are not registered. | Operators should not be able to browse student records (blueprint section 2). | 2026-10-12 |
| B12 | Unauthenticated requests | Answered with 401, not DRF's default 403. | Lets the frontend tell "signed out" from "not allowed" without guessing. | 2026-10-12 |
| B13 | Free text in Phase 2 | Two short fields only: a trigger's `label` (80 characters) and an episode's `what_helped` (200). Both are encrypted at rest with Fernet (`FIELD_ENCRYPTION_KEYS`), never logged, and excluded from any email. The blueprint's optional episode "description" is not built. | The features need the person's own words, but long open text is the hardest data to protect, so it is kept short and encrypted (same reasoning as D4). | 2026-10-12 |
| B14 | Scales | Mood, sleep quality, energy, stress and episode intensity all use 1 to 5. Sleep duration is hours with one decimal. | One scale everywhere keeps the check-in under 20 seconds and the controls large. | 2026-10-12 |
| B15 | Second check-in on the same day | `POST /check-ins` replaces that day's check-in (200) instead of failing. | No error state on a flaky phone connection, and still exactly one row per day. | 2026-10-12 |
| B16 | Back-dating check-ins | Allowed up to 7 days back, never forward. The date cannot be changed afterwards. | Lets someone fill in yesterday without making history freely editable. | 2026-10-12 |
| B17 | Which local date a check-in gets | The date in the person's time zone at the moment of saving, using the zone database (daylight saving aware). Changing time zone later does not rewrite past check-ins. | A late-night check-in belongs to the day the person was living in. | 2026-10-12 |
| B18 | Unreviewed content | Hidden from the API unless `SHOW_UNREVIEWED_CONTENT` is on; production settings force it off. When shown, items carry `reviewed: false`. Draft and retired content is never served. | Non-negotiable 8: placeholders must not be able to reach students. | 2026-10-12 |
| B19 | Pattern observations | Shown only with 6+ paired days, 2+ days on each side of the person's median sleep, and a difference of 0.5 or more. Otherwise a neutral "not enough yet" line. | Avoids reading meaning into noise. | 2026-10-12 |
| B20 | Exercise feedback | An append-only event log per user; "hidden" is derived from the latest hide/unhide event. Events can be deleted, not edited. | Simple, reversible, and fully exportable. | 2026-10-12 |
| B21 | Free text in Phase 3 | The safety plan (three lists, 12 lines of 200 characters each) and a contact's name, email and relationship. All encrypted at rest, never logged, never in the admin. | These features cannot exist without the person's own words; the same limits as B13 apply. | 2026-10-12 |
| B22 | Number of trusted contacts | At most 3 per student. | Keeps sharing deliberate and limits the app's use for bulk email. | 2026-10-12 |
| B23 | Invitation limits | One invitation on adding, at most two re-sends, at least 24 hours apart. Links last 14 days. If the contact does nothing, nothing more is ever sent. | The contact did not ask to hear from the app. | 2026-10-12 |
| B24 | Unsubscribe and do-not-email | Any email to a contact carries an unsubscribe link and a one-click `List-Unsubscribe` header. Unsubscribing withdraws every consent involving that contact. The contact may also block the address for every student. A permanent bounce or spam complaint blocks it automatically. The block list stores keyed fingerprints, not addresses. | A person who says stop must stay un-emailed, without the app keeping their address to do so. | 2026-10-12 |
| B25 | Weekly note needs re-confirmation | A weekly note pauses itself if the student has not confirmed it for 90 days (`CONSENT_RECONFIRM_DAYS`). Resuming counts as a confirmation. | Consent given long ago and forgotten should not keep sharing indefinitely. | 2026-10-12 |
| B26 | What "preview and confirm" means technically | Turning the note on requires the current notice version, a hash of the current message wording (from the preview), and `confirmed: true`. Any mismatch is refused. | Proves the student was shown the current notice and message, rather than trusting the client. | 2026-10-12 |
| B27 | Weekly note schedule | The student picks a weekday and hour in their own time zone (default Monday 09:00). The note covers the 7 full local days before the send. Times are computed with the zone database, so the local hour is kept across daylight-saving changes; changing time zone reschedules. | Predictable and visible to the student. | 2026-10-12 |
| B28 | Delivery is at-most-once | A notification is marked "sending" and committed before the provider is called. If a worker dies mid-send it is never retried; it ends as "failed / outcome unknown". Transient provider errors are retried up to 5 attempts (after 1, 5, 15 and 60 minutes). | Sending a weekly note or an SOS twice is worse than a visible failure. | 2026-10-12 |
| B29 | SOS message text | Fixed wording; the student cannot edit it. They choose the recipient, see the exact text, and confirm. The request must quote the hash of what was shown. | Guarantees that what is sent is what was approved, and stops the feature being used to send arbitrary content. | 2026-10-12 |
| B30 | SOS limits | 3 an hour (rate limit) and 6 in 24 hours (counted in the database, so it survives a cache reset). The limit message points to helplines and the safety plan. | Limits misuse and repeated messages to one person, without leaving the student at a dead end. | 2026-10-12 |
| B31 | SOS reply wording | The API says the message is "queued" and that the app cannot tell whether it was read. It never says sent, delivered or alerted. Delivery status is available separately. | Non-negotiable 5. | 2026-10-12 |
| B32 | Resources are public | `GET /resources` needs no sign-in. | Helplines must be visible before sign-up and cacheable offline. They contain no personal data. | 2026-10-12 |
| B33 | Stale resources | An entry is stale 90 days after its last verification, or if never verified. Stale entries are still listed, with `stale: true`. A command flags them and can fail a release pipeline. | A possibly-outdated number, clearly marked, is more useful than a missing one; but it must not go unnoticed. | 2026-10-12 |
| B34 | Audit retention | All audit events, not only those of deleted accounts, are purged after 12 months. A student's visible consent history comes from their consent records, which live as long as the account. | Data minimization; D5 set the period. | 2026-10-12 |
| B35 | Audit contents | Action name, object type and id, and metadata limited to five allow-listed keys (purpose, notice version, reason, status, scope). No free-text column exists. | Makes it structurally impossible to write message text into the audit trail. | 2026-10-12 |
| B36 | Do-not-email fingerprints are kept indefinitely | They survive account deletion and have no expiry. | Forgetting a "do not email me" request would break it. A fingerprint identifies nobody without the server secret. Flagged for legal review (R8). | 2026-10-12 |
| B37 | Bounce and complaint webhook | A generic endpoint authenticated by a shared secret, taking a message reference and an event type. Disabled unless configured. | The provider is not chosen (Q1); this keeps provider specifics out of the app and never puts an address in the request. | 2026-10-12 |
| B38 | How the browser reaches the API | Through a same-origin proxy in the frontend (`frontend/src/app/api/v1/[...path]/route.ts`). The browser never calls the API host directly. | Cookies are first-party, there is no cross-origin configuration to get wrong, and the API address is a runtime setting. The CORS allowlist stays in place for any direct client. | 2026-10-12 |
| B39 | No Framer Motion | Transitions use CSS only. | It would add roughly 40 KB to every screen for effects CSS already does, against the performance budget. README C.9 lists it as a recommendation, not a requirement. | 2026-10-12 |
| B40 | Hand-written service worker instead of Serwist | `frontend/public/sw.js`, about 100 lines. | Next.js 16 builds with Turbopack, which the Serwist plugin does not target, and a small explicit worker makes "never cache /api/" easy to read and test. | 2026-10-12 |
| B41 | Device preferences stay on the device | Theme, text size, reduced motion and low-bandwidth mode are saved in the browser only. Language is the one preference also saved to the account. | They are comforts of a device, not account data; nothing is gained by sending them to the server. | 2026-10-12 |
| B42 | What is kept on the device for offline use | The safety plan (removed on sign-out and account deletion), the helpline list and exercise texts. Nothing else. The service worker caches pages and static files, never an API response. | Decision D7 needs the plan and helplines offline; everything else stays on the server. A browser test checks both stores. | 2026-10-12 |
| B43 | Support is a page, not a dialog | `/support` is a plain link on every screen, and its four options are sections of one page. | A link works offline, before scripts load, with a keyboard and with a screen reader. Nothing on it moves unless the person starts the breathing aid. | 2026-10-12 |
| B44 | Accent color adjusted for contrast | `--lumen` is `#8F88F5` in Night, a little lighter than the README's `#7C74F2`, and primary buttons use the pale `--lumen-hi` fill with dark text. | Meets WCAG AA for text on the dark background; README C.3 allows refining values while keeping roles. | 2026-10-12 |
| B45 | Response types | Hand-written Zod schemas in `frontend/src/lib/schemas.ts`, matching the OpenAPI schema, rather than generated code. | Small, readable, and validates responses at run time. A generator can replace it later without changing screens. | 2026-10-12 |
| B46 | The mood scale wording | 1 to 5 as "Very low, Low, In between, High, Very high"; the same words for energy and stress; sleep quality from "Very restless" to "Very restful". | Neutral, evenly spaced, no "good" or "bad". Flagged for review (R17). | 2026-10-12 |
| B47 | Offline with an unverifiable session | When the device has no connection, the signed-in screens still render so the device copies are reachable. Every other request fails and says so. | Otherwise the saved safety plan would be locked behind a session check that cannot run offline. | 2026-10-12 |
| B48 | Crisis handling in chat | A deterministic check in code (`apps/chat/safety.py`) runs on the student's message before any model is called, and on the model's reply after. A match returns a fixed human-written reply with routes to Support, the safety plan, helplines and a trusted contact. The message is never sent to the provider. | Decision D8 and non-negotiable 3: a prompt is not a safety mechanism, and no classifier may alert anyone. | 2026-10-12 |
| B49 | The safety check is a wide net | It prefers false alarms to misses, covers common misspellings, obfuscation, romanized Hindi and Devanagari, and stores no risk label about anyone. Two levels: crisis and acute distress (panic). | A false alarm shows a calm message with options; a miss would send a crisis message to a language model. | 2026-10-12 |
| B50 | No reviewed material, no model call | If retrieval finds no approved passage sharing at least two terms with the question, the chat replies with fixed text and does not call the provider. | More conservative than the blueprint's "reflective support": an ungrounded model is the riskier path, and this also costs nothing. | 2026-10-12 |
| B51 | Transcripts | Off by default: nothing is written to the database and the browser holds the conversation. Opt-in saving is encrypted, capped at 30 days, and turning it off deletes what was saved. | Locked decision D10. | 2026-10-12 |
| B52 | What the AI provider receives | Fixed instructions, up to three reviewed passages, the message, and at most six earlier turns. Never a name, email, user id, check-in, safety plan or contact. | Data minimization (D10). A test inspects the request. | 2026-10-12 |
| B53 | Embeddings are local | Passages and questions are embedded by a deterministic hashing embedder in `apps/chat/knowledge.py`, stored in pgvector. No text is sent to an embedding provider. | No extra processor, no network in tests, reproducible. It matches vocabulary, not meaning; a semantic model can replace it later. | 2026-10-12 |
| B54 | Chat provider and model | An adapter (`apps/chat/providers.py`). Local and tests use `MockProvider`. Production defaults to `AnthropicProvider` with `claude-opus-5-5`, low effort, and the API's default refusal fallback; the key is read from `ANTHROPIC_API_KEY` by the SDK. | Answers question Q2 with a default the owner can change by setting `CHAT_PROVIDER` and `CHAT_MODEL`. | 2026-10-12 |
| B55 | The model's reply is not trusted | Replies are checked in code for diagnoses, medication advice, claims of monitoring or alerts, and persona or instruction leaks. A failing reply is discarded and a fixed reply shown. | Prompt injection and model error are handled the same way: by not showing the output. | 2026-10-12 |
| B56 | Budgets | 10 messages a minute, 40 AI replies a day per student, 2000 a day for everyone. Fixed safety replies are never limited. | Cost ceiling and abuse control without ever blocking the safety reply. | 2026-10-12 |
| B57 | API responses are never stored | `NoStoreApiMiddleware` adds `Cache-Control: no-store` to every `/api/` response, and the service worker never caches `/api/`. | A shared or borrowed phone must not keep a copy of someone's records in a cache. The offline safety plan is a deliberate, separate copy the student can clear. | 2026-10-12 |
| B58 | Content-Security-Policy is partial | The frontend sends a policy that restricts framing, form targets, objects and connections, but still allows inline scripts, which Next.js needs without per-request nonces. | A nonce-based policy forces every page to render dynamically; recorded as open finding S3 rather than done badly. | 2026-10-12 |
| B59 | Images are tagged by commit only | Images are published as `sha-<full commit>` (plus a release tag for `v*`). There is no `latest`. Deploys name a commit. | A deploy and a rollback must each point at exactly one build. | 2026-10-12 |
| B60 | Migrate first, then replace | `infra/deploy.sh` runs migrations with the new image while the old version serves, then replaces the containers, then runs smoke tests. Migrations must be backwards compatible and are never undone automatically. | Avoids downtime and makes a code-only rollback safe. | 2026-10-12 |
| B61 | Deployment target | A generic Linux host running Docker Compose, reached over SSH, with managed PostgreSQL and Redis. No platform-specific tooling. | Question Q3 (which host) is unanswered; this works on any host and commits to none. | 2026-10-12 |
| B62 | Failed sends are never retried after a restore or a sweep | `sweep_stuck` marks an unfinished send as failed; it does not send again. | At-most-once: a duplicate note or SOS to a contact is worse than a missing one the student can see and resend. | 2026-10-12 |
| B63 | Public pages follow the owner's references closely | Pure black, dithered scenes of light (held light, a figure, two people on a hillside), hairline grid, corner marks, square controls, mono labels, film grain. Replaces the earlier "references are mood only" reading for the landing, sign-in and footer. | Owner's direction on 2026-10-12 after seeing the first design. Accessibility and low-data rules are unchanged. | 2026-10-12 |
| B64 | Scenes are generated, not photographed | Every scene is drawn by code (`frontend/src/components/scene/fields.ts`). No stock image, no AI-generated image, no likeness of a person. Stills are committed PNGs (63 KB in total); low-bandwidth mode downloads none of them. | No licensing question, tiny downloads, and both themes come from one source. | 2026-10-12 |
| B65 | Local email goes through real SMTP | The local stack includes Mailpit (`axllent/mailpit:v1.27.11`), a mail server that catches every email and shows it at http://localhost:8025 without delivering it. The app sends to it over SMTP, the same path as production. Real delivery needs only the provider's SMTP settings in `.env`; `manage.py send_test_email` checks them. | The owner needs email to work as a feature. Catching locally means a test can never email a real person by accident. | 2026-10-17 |
| B66 | Every section is in the main navigation | The More page is removed (its address now opens Home). Phones get a two-row bar of ten sections; desktop a left rail. Sign out moved to Settings. | The owner asked for nothing to be hidden in a menu. | 2026-10-17 |
| B67 | The Support button reads "SOS Support" | The button on every screen now says SOS as well as Support. It still only opens the Support screen; nothing is sent until the student chooses a contact, reads the exact message and confirms. | The owner could not find an SOS button. Wording needs safeguarding review (R25). | 2026-10-17 |
| B68 | Free text, in one place only: Vent | Amends D4 at the owner's request. The check-in stays taps only. Vent accepts free text, and by default keeps none of it: the text is sent once to our own API to get a reaction and is not stored or logged. Keeping an entry is a separate, explicit switch; kept entries are encrypted, exported, deletable one by one, and erased with the account. Never sent to email, the AI chat, analytics or Sentry. | The owner asked for a place to write freely. This is the most private way to offer it. | 2026-10-17 |
| B69 | The vent figure reacts to words, in code | `apps/vent/reactions.py` counts words from short lists and picks one of seven reactions. No AI provider, no stored label, no score. The same crisis check as the chat runs first and always wins: the figure stays steady and the screen shows Support, the plan and helplines. Nobody is notified. | A reaction is a mirror, not an assessment (non-negotiables 1 and 3). Keeping it deterministic means it can be reviewed and tested line by line. | 2026-10-17 |

## Open questions

These are for the project owner. Until answered, the stated default is used.

| # | Question | Default until answered |
|---|---|---|
| Q1 | Which transactional email provider (Resend, Postmark, other)? | Provider-agnostic adapter; console backend locally; no provider SDK is hard-wired. |
| Q2 | Which hosted LLM provider and model for Phase 4? | Answered by default in B54 (Anthropic, `claude-opus-5-5`); confirm, and review the provider's data terms (R13). No real key has been used: only the mock has run. |
| Q3 | Where will the API, worker, database and Redis be hosted? | Generic Docker host with managed PostgreSQL and Redis; frontend deployable to Vercel or as a container. |
| Q4 | Exact wording of the fixed neutral line in the weekly email. | README example: "This is a routine weekly note. Silence does not mean anything either way." Marked NEEDS_HUMAN_REVIEW. |
| Q5 | Default timezone for new accounts. | Browser-detected timezone sent at registration, falling back to `Asia/Kolkata`. |
| Q6 | Chat transcript retention period when a student turns transcripts on. | 30 days, user-adjustable downward, deletable at any time. |
| Q7 | Who is the named human owner for helpline verification, and how often? | Unassigned. Entries older than 90 days are flagged stale; release is blocked on re-verification. |
| Q9 | Should the patterns screen show the "You checked in on X of the last N days" line at all? | Shown, as a plain count with no judgement. Flagged for review under R10. |
| Q10 | Should a student be able to add an optional short line to the SOS message? | No. Fixed text only (B29). |
| Q11 | Should the 112 emergency entry be in the seed at all? | Included as an unverified placeholder alongside Tele-MANAS; both are hidden until verified. |
| Q8 | Final product name and sender domain for email. | Working name only; sender address comes from environment. |
